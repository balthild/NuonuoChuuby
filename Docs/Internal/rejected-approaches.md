# 试过并否决的方案

每条都记**否决它的证据**，不是印象。重开之前先看这里的数字。

## 120 fps 直接渲染（否决）

把 tick 提到 120 Hz、去掉插值，让位置按显示器自身频率更新、没有插值滞后。
精灵帧本身只有 11–18 fps，所以位置是唯一能变的东西 —— **视觉上与插值相同**，
真正差别只有约 12 ms 的延迟。

实测（同一构建 + 启动开关，三次 12 s 连续拖动）：主线程 887 vs 859 ms ——
**120 Hz 直接与插值在拖动时成本相当（+0.23%）**。但用户用 `htop` 看了更长的、
基本不在拖动的时段，看到**平均 CPU 约 +1%**，不可接受。用户的读数获胜。

**我的 A/B 为什么低估了它（值得留住的教训）**：我测的是连续拖动，但提高 tick 率的成本
主要是**每 tick 固定工作翻倍** —— tick 即使她站着不动也每秒触发 120 次。拖动被拖动工作主导，
掩盖了 idle 的增加。idle 时 `step` 占主线程 78%，而其中**没有按时间门控**的部分
随 tick 翻倍。**评估任何提高 tick 率的东西，要测稳态/idle。**

## 拖动绘制降到 30 Hz（否决）

用户想试「把拖动时图像的绘制频率从 60 降到 30」（靠 CA 插值补到 120）。

「绘制频率」在这个项目里就是**拖动中 `step()` 每 tick 调 `notifyPlacementIfChanged()` 的频率**
（写 `layer.position` 那一步）；物理仿真本来就是 60 Hz。
旋钮（已撤销）：`dragDrawInterval` + `placementAnimationDuration`
（glide 时长必须跟着变成该间隔，因为 **D 必须 = T**，见 `rendering.md`；
只降绘制不降 glide 会「滑一下停一下」）。

**实测：htop CPU 约 −1%，但拖动手感明显变差，不值得。** 用户撤销了全部更改，没有留下提交。

为什么省得有限：只减了**一半的 CA 动画事务**，物理 tick 仍 60 Hz；而手感变差是必然的 ——
跟手延迟 = `v·D`，`D` 从 1/60 变 1/30 就是延迟翻倍。平滑度与延迟是同一个参数。

若日后还想试：想省更多就必须把**拖动期间整个 tick**（物理也降）降到 30 Hz，
那是另一个（物理保真度）取舍，且要用同一脚本 A/B。

## 用 kqueue 替代 FSEvents（否决）

用户曾提出用 kqueue（「监听桌面不需递归」）。否决理由：

1. kqueue 在目录 fd 上只报「该目录变了」，**不给文件名**，必须自己 diff 目录列表才知道删了什么；
2. 目录 diff 拿不到「删除前」的图标位置，而 AX 索引恰恰能；
3. FSEvents 本就按路径注册、非递归语义可控，还带 per-file 标志。

（注：本机上 `open(O_EVTONLY)` 现在不阻塞了，因为此机 Desktop 已不是 iCloud 托管 ——
但这不改变 ①② 的结论。）

## 用 `AXObserver` 通知替代追读轮询（否决）

想用 AX 通知替掉「新图标出现后每 0.25 s 读一次」的轮询。实测（真机、Finder 建/删文件夹），
**19 个通知名在 app 与 icon container 上全部注册成功**（注册成功 ≠ 会触发）：

- **`AXCreated` 从不触发** —— Finder 不为桌面图标发它。这是否决的决定性事实。
- `AXUIElementDestroyed` 会触发（删除后 ~0.2–0.3 s），**但那时元素已失效**：
  所有属性都是 `kAXErrorInvalidUIElement`，**读不到位置**。所以它既不能替代 FSEvents 的删除检测，
  也不能替代活读。
- 创建期唯一会触发的是 `AXSelectedChildrenChanged`（+0.18…+1.36 s 共 6 次），
  但它语义是「选中项变了」，只是因为 Finder 会**选中**新建的文件夹才顺带触发；
  拖入/下载等不改变选中的创建不会触发它 —— 作为「出现」信号不可靠。

**结论：追读轮询保留，这是唯一可用的方式。**

## 把她的窗口夹在另外两个窗口之间（不可行）

`NSWindow.level` 是粗粒度整数，**所有**普通窗口都在 `CGWindowLevel 0`，
所以「A 和 B 之间」没有可用值；降低层级会掉到 Dock（20）与菜单栏（24）之下；
二维裁剪也不行（窗口投影由**遮挡者**画，且窗口不都是矩形，裁成矩形仍会从两者里透出）。
详见 `physics.md` 的「被覆盖的封闭盒」。

## 鼠标移动开销：所有窗口级/连接级开关都无效

背景与机制见 `performance.md`。以下是**逐个实测**的结果。

| 手段 | 层级 | 结果 |
| --- | --- | --- |
| 会话全局 `CGEventTap` 丢弃 `.mouseMoved` | 会话 | **有效，−80%**（app Δ +6.07 → +1.0…+1.4，`NSEventThread` 样本 420 → 0），但**所有 app 都失去 hover** |
| `ignoresMouseEvents = true`（公有） | 窗口 | 只省 **~0.36 pt（约 13%）**，且点击/拖动/捏脸全废 |
| `CGSSetWindowEventMask(mask: 0)`（私有） | 窗口 | 无变化 |
| `CGSSetWindowTags` + `CGSTagTransparent`（私有） | 窗口 | 无变化 |
| `CGSSetMouseEventEnableFlags(cid, wid, false)`（私有） | 窗口 | 无变化，**且调用本身在本机是空操作** |
| `CGSSetEventMask`（私有，连接级） | 连接 | 无变化（投递计数相同） |

### 关于那个 StackOverflow 答案

问题：*Opaque NSWindow and WindowServer poor performance*（SO #59309522）。答案把过载归因于
`ignoresMouseEvents` **未设置**时的「第三态」——每次鼠标移动做一次透明命中测试，
并说显式设 `true` 即可消除。

**它不是我们的成本。** 我们设了（用户确认有效：拖不动她），app 与 ws 都没动；
而且那个 13% 的节省来自投递**之后**的路由，不是命中测试。
（他们的复现用 5000 个 layer，我们 overlay 只有约 3 个，本来也不太可能撞上。）

### 为什么私有调用返回 0 不能当证据

`CGSSetMouseEventEnableFlags` 头文件承诺「为否时事件传给下一个窗口」，
实测点击**仍被前景窗口接收**，而同一探针里的 `ignoresMouseEvents` 对照能把它送到后面。
**这些私有 API 返回 `kCGErrorSuccess` 并不代表生效 —— 必须验证副作用。**

同类陷阱：`CGSGetWindowTags` **对每个 tag 都读回 0**，无法确认写入；
`CGSSetWindowTags`/`CGSGetWindowTags` 的 size 参数**必须是 32**（否则返回 `kCGErrorFailure` 1000）；
而 `CGSTagTransparent` **确实生效**（点击穿透），只是**只对点击**，不影响移动流。

### 「tag + CGEventTap 按距离动态切换」也不成立

- tag 根本不 gate 移动流，**没有可切换的东西**；
- 即便只用全局 tap 做动态切换：成本是「光标在哪里移动」就付的，而 overlay 铺满全屏。
  只在光标**远离**她时丢弃 ⇒ 等于绝大部分时间全系统关闭 hover；
  只在**靠近**她时丢弃 ⇒ 一点都省不到。
- 唯一能省的是会话全局销毁事件，而它必然影响所有 app。

## 用 Accessibility 做窗口跟踪（否决）

拿不到 z 序，而 z 序是遮挡减法的唯一输入；没有公开的 `AXUIElement → CGWindowID` 映射；
只覆盖实现了 AX 的应用（Java / X11 / 部分游戏窗口不报）；逐属性读取是跨进程 IPC，
对方应用卡住时会阻塞。它改善的也只是「新窗沿被发现」的延迟，不是用户感受到的跟随延迟。
Ledgeling 的 macOS 层同样只用 `CGWindowListCopyWindowInfo`。

**桌面图标坐标是 AX 的正确用途**（那里只有 AX 能给出真实坐标），见 `meal-and-icons.md`。

## 用固定常数 RNG 替代可播种 RNG（否决）

用户问过「要不要加一个测试专用 RNG、永远返回固定数」。结论是不要：

1. **确定性早就有** —— `TestAssets.randomSeed` + `PetRandom` 已经是逐位可复现；
   「固定数 RNG」不会让非确定的东西变确定。
2. 真正的缺陷是**测试编排**（判定窗口里混进了不属于它的行为），任何 RNG 都改不了。
3. 「固定数」消掉了「序列漂移」这一种脆弱，却换来另一种（红绿取决于常量是否巧合通向方便行为），
   且**两个测试无法共存**（同一 draw 站点一个要打滑一个要成功，单常量给不了）。

若日后真需要「依赖特定随机结果」的测试，正解是**可编排脚本序列**的 RNG，
而不是「永远同一值」。**优先用领域接缝（`quietMode`）而不是随机性 hack。**

## 从 stub 之外删除 Trash 佐证（已做，非否决）

原版监听 Windows `$Recycle.Bin` 读原始路径，那是它的主检测手段；macOS 无逐项元数据，
移植时 Trash 被降级成「佐证」。但它也不能纠正误吃，且 `cameFromTrash` 只赋值、无读取方。
**`rm` 等直接解链的删除根本不进回收站**，所以「Trash 里没有」什么都证明不了。
现已删除，沉降窗从 2.5 s 改成 0.5 s。详见 `meal-and-icons.md`。
