# 性能：实测数据与方法

> 所有数字都是**某台机器某个时刻**的，只用来看比例和方向，不要当常量引用。

## 怎么测（先读这条，踩过的坑最多）

- **测量 CPU 时间，不是 wall time**：`getrusage` 每秒（user+sys），或用 `CLOCK_THREAD_CPUTIME_ID` 归
  因到单次调用。一次窗口服务器查询的 wall time 主要是 `mach_msg` 等待，那不是我们的 CPU。
- **永远用 `make rerun` 测**（LaunchServices 路径）。直接 exec `Contents/MacOS/NuonuoChuuby` 会报
  ~10–16%，而同一二进制正常启动是 28–38%。这个差异造成过好几轮错误结论。
- **紧循环微基准会撒谎**：循环里调 `setFrame` 测到 27 µs，因为 CoreAnimation 合并了提交；真实在
  run-loop 轮次之间的成本是 230–310 µs。窗口服务器查询同理：循环里 25 µs，应用里约 300 µs。**永远不
  要相信窗口服务器/AppKit 调用的紧循环微基准。**
- **量「某一次调用」自己的成本，用 `getrusage(RUSAGE_SELF)` 把它包起来**，比 trace 归因可靠：xctrace
  导出只有 Running 行，会系统性低估阻塞在 `mach_msg` 里的纯 IPC 调用。同一个公有整表枚举，trace 给
  ~0.4 ms、`getrusage` 给 ~0.83 ms，而后者与「枚举占 idle 一半」的 A/B 自洽。（`RUSAGE_THREAD` 没被
  Swift 导入，用 `RUSAGE_SELF`；几百 µs 的窗口里其它线程的份额是常数偏移，两个模式同样付出。）
- **对比两个运行要有内部控制**：找出一个「不是你改的东西」的每帧函数，确认它被同等次数地执行（见
  `rendering.md` 气泡那段）。
- **A/B 必须跨进程交替**：同一进程连跑 3 次只是精确估计「那一次启动」。实测同一条件的两个进程分别给
  出 +6.38/+6.44/+6.45 与 +4.45/+3.97 —— 进程间方差足以把 0.85 pt 的假效应伪装成 13%。**交替启动**，
  并拿一个本该相同的启动做 sanity check。
- **提高 tick 率的改动必须测稳态/idle**：拖动被拖动本身的工作主导，会掩盖 idle 的增加。
- **测 idle 前先把她的状态钉死**：quiet 模式让她在 `idle` / `sleeping` 之间随机抽，两个状态成本不
  同，**同一二进制 4 轮能差 1.33 pt**（0.19 是钉住后的水平）。改 `life-state.json` 的 `sleepiness =
  100` 让她必然睡 —— 两个状态都不跳过枚举，所以只影响渲染成本。**别把这个差当成机器负载。**
- `top -l 1` 的进程百分比是 0；前两个采样也不准，第三个起才精确。滞后的形状是 `100*s/(s+0.85)` 而不
  是平滑窗口。`ps -o %cpu` 与 `htop` 正确。
- xctrace 导出里**只有 Running 行**（没有 Blocked），所以**栈归因系统性低估阻塞型开销**（比如
  `waitUntilExit()` 的 100 ms 卡顿）。这类开销只能靠 A/B 看出来。
- 采样计数**不能**当分母：便宜的符号被采样得更少，分母会跟着被测对象移动。用自己记的精确计数器（例如
  拖动结束时的 `DragProfile` 事件）。

### xctrace 导出解析

`xcrun xctrace record --template 'Time Profiler' --attach <pid>` 可用于归因，但**排最内层帧会误
导**：多数样本是分配器 / CoreFoundation / CA 提交的杂音，没有单一热点。应当统计「样本的调用链**包
含**符号 X」的占比。

导出 XML 有 id/`ref` 去重：首次出现内联定义（带 `id`），后续行只给 `ref`。**直接 grep 原始 XML 或逐
行解析会只看到一行。** 必须先解析 `frame`/`backtrace`/`thread`/`thread-state` 的**两种**形式，再按样
本聚合。`_ignored/scenario-bench/top_symbols.py`（gitignored，不在仓库里；`--all-threads` 按线
程，`--symbol` 列出含某符号的调用链）就是这套工具。早先的 `.build/traces/analyze.py`、`chains.py` 已
不存在。

**只认 `ref` 的解析器会静默出错，而且看不出来。** 样本行里的 `backtrace` 大多**内联**（每行一份、带
`id`），把它们当成未解析会让整条样本落进「未归因」：分母仍是全部样本，于是**所有符号的占比被系统性压
低**，而输出照常有数字。**自检**：两种形式都要查；未归因样本的权重应接近 0，不接近 0 就先修解析器，
不要读数。

**阻塞型调用的 inclusive 归因会低几倍，而且只覆盖一部分调用。** 2026-11-04 用两轮 Time Profiler （同
一份活动、改前 / 改后）量过：`SLWindowListCopyWindowInfo`（未被改动过）在改前那轮是 **761 ms / 571
s**，而按代码里的节流（10 Hz body + 2 Hz 图 = 12 次/秒）和探针里**裸调用**的单次成本（0.35 ms，不含
Swift 桥接）算，真实值应是 **~2.4 s** —— **低约 3 倍**。机制是**采样分辨率**：一次调用只花 0.35 ms，
而采样器每 1 ms 打断一次线程，所以多数调用落不进任何样本；落进去的那次又被整记成一个样本（1 ms），于
是**被采到的是 1 ms 而不是 0.35 ms**。两个方向的误差不会抵消。

同一份 trace 只数得出约 **1.6 次/秒** 的枚举 burst，也就是按代码推算的 **12 次/秒里只有约 13% 在栈上
留下了痕迹**（**注意：这个比值不是「trace 只跑了 13% 的时间」** —— 采样在 1 kHz 上，13% 说的是被采样
到的调用）。所以：

- **绝对成本不要从 trace 反推** —— 用 `getrusage` 包住调用，或用探针。
- **两轮的逐秒归一漂移可达 ±10%**，比一次小改动的总效应还大：同一次实验里，未被改动的 `SL` 漂了
  **+12.5%**、活读漂了 **−5%**。想量总量必须跨进程交替做 A/B（上一条）。

## 时间预算

- idle / 走动 / 拖动：**4–5% / ~25% / 28–38%**（改进前）；盒内 idle 在 30 Hz 节流后 **3.4%**。
- 早期写下的 `< 0.5%` idle 预算**从未测量过**，来自原版 Windows 的数字，对 60 Hz 透明 overlay 不是现
  实目标。
- **debug ≈ release for idle CPU**：idle 成本是框架 + run loop + 两次窗口枚举，不是我们的 Swift。不
  要用「release 更快」解释 idle 成本。
- 非主线程成本 0.01–0.2%。旧说法「约 4 个百分点在 CoreAnimation 线程上」是错的。

## 热点与它们真实的量级

| 项 | 成本 | 备注 |
| - | - | - |
| 窗口服务器单窗口读 | **~300 µs CPU**（应用内） | 紧循环只有 25 µs，见上；**已由私有读替代，46 µs** |
| 全量枚举（10 Hz body + 2 Hz 图 = 12 次/秒） | **0.86 → 0.44 ms/次**（探针，2026-11-04） | 盒外 idle 的最大单项，见下 |
| 30 Hz 盒内重读 | 1.3–1.6% 绝对 idle | 盒内 idle 的最大单项；**改为私有读后按 30 Hz × 46 µs 折算约 0.14%** |
| `setFrame` | 230–310 µs/次 | 只有移动时，不是 idle 成本 |
| 一条 `writeEvent` 日志 | **45.4 → 26.3 µs** | 去掉每行 `stat` 后 |
| 一次 AX 全量枚举（~21 图标） | ~11 ms | 主线程 |

窗口服务器读的**可信数字来自整个应用 A/B**：跳过 45 次读/秒省了 1.3–1.5 个点 ⇒ **每次约 300 µs**（应
用内探针说 70–120 µs，A/B 更可信）。

### 盒内重读的 30 Hz 节流

`isResting` 时盒子以 30 Hz 重读；读到移动就恢复逐帧。`x == previousBox` 对未移动的窗口是精确的
（CGWindowList 的矩形是整数），所以跳过的帧是真的静止帧。

实测（盒内、idle、11 个 `top -l` 采样、丢掉第一个）：debug 5.01/5.38 → **3.42**； release 4.75 →
**3.44**。15 Hz 只到 3.85，所以 30 Hz 用一半的延迟拿到约 80% 的收益。 **取 30。** 代价是「发现盒子移
动最多晚 33 ms」以及随后一次追赶帧 —— 已明确接受。

### 单窗口活读改用私有 `CGSGetWindowBounds`（2026-10-26）

她站在窗口上或盒子内时，每帧要问「这个窗口的矩形现在在哪」。之前走
`CGWindowListCopyWindowInfo([.optionIncludingWindow])`，而它为了四个数字构建整份窗口描述。改用私有
`CGSGetWindowBounds` 后（`Platform/WindowServerBounds.swift`，`dlopen` 解析、失败即回落公有读）：

- **293 µs → 46 µs / 次**（trace 内 inclusive，见下），约 **6 倍**。
- 盒内 idle：**2.87 → 2.19% 单核**（−0.69 pt，**−24%**）。两轮范围不重叠。
- Window Server 侧 45.0 → 43.9，在噪声内 —— 这项成本本来就在我们进程里。

**A/B 方法**：4 轮交替（`cg,cgs,cgs,cg`），每轮 `make rerun` 重启，20.35 s `getrusage` 差值，同时录
20 s Time Profiler。每轮都有**同样的内部控制**：600 次活读、0 次回落、 0 次状态转换、盒子内心跳
2/2。省下的 148 ms / 20.35 s = 0.73 pt 与实测 0.69 pt 对上账。

**必须分开的两个 `SLWindowListCopyWindowInfo`**：`cgs` 轮的 trace 里仍有 83–103 ms 的公有读，那是
`MacOSPlatform.windows()` 的周期枚举（2 Hz 图 + 10 Hz body），两轮相同。把它和活读混在一起算，会把没
变的成本记到被比较的那一项上。

**一处要更正的旧数字**：`rejected-approaches.md` 曾记「2.5 µs、便宜 12 倍」，那是**紧循环**读数。app
内 46 µs 对 293 µs ⇒ 真实约 **6 倍**。与 `setFrame`（循环 27 µs / 真实 230–310 µs）、单窗口枚举（循
环 25 µs / 真实 ~300 µs）是同一个陷阱：**私有调用的紧循环微基准尤其不可信，它连 IPC 都不会真的发
生。**

**未测**：站在窗口顶边（`liveSurface`，60 Hz，预期收益翻倍）、多显示器。等价性验证只覆盖**在屏**窗
口；最小化 / 其他 Space 的窗口没比较过 —— 两个调用点问的都是她在其上或其中的窗口，按定义在屏，所以这
不构成风险，但也**不要把结论外推**。（整表枚举能否也改私有已试过并**否决**，见下。）

### 整表枚举改 CoreFoundation 直读（2026-11-04）

`MacOSPlatform.windows()` 原来把 `CGWindowListCopyWindowInfo` 的结果 `as? [[String: AnyObject]]` 桥
接成 Swift 的数组套字典，然后每个字段一次 `as?`。改成在 CF 对象上直接读（`MacOSPlatform.swift` 里
file-private 的 `WindowDescriptionRead`）。

- **单次枚举 0.86 → 0.44 ms**（探针 `_ignored/cf-read-probe/main.swift`，线程 CPU，60 Hz timer 驱
  动，两个读法交替，19 窗口）。桥接部分占原来的一半。
- **等价性**：与桥接读法在真实桌面上逐字段比对 **200 轮 / 3800 条目，零差异**。
- **行为差异（更严，不是更松）**：bounds 字段缺失时两者都丢弃该窗口；而字段**类型**不对时
  `CGRect(dictionaryRepresentation:)` 会在 CoreGraphics 里**抛异常**（对 NSString 发
  `_getValue:forType:`），新读法丢弃该窗口。
- 字段的真实存储类型是量出来的，不是猜的：`kCGWindowNumber` / `OwnerPID` / `Layer` 是 **SInt64**，四
  个 bounds 字段与 `Alpha` 是 **Float64**（`CFNumberGetType`），所以读它们不转换。

**trace 能证明的是结构，不是绝对量**（原因见上面的「xctrace 导出解析」）：

| | 改前 | 改后 |
| - | - | - |
| `windows()` 里除 `SLWindowListCopyWindowInfo` 之外的部分 | 202 ms | **13 ms** |
| 栈上所有桥接帧（含被内联后游离到调用帧之外的） | 527 ms | **24 ms** |

即**改后这个枚举里已经只剩服务器往返**，没有别的可删；再往下只能砍次数（`todo.md` 第 5 节第 1 条）。

**绝对收益没有做受控 A/B**，只有推算：−0.43 ms/次（探针）× 12 次/秒 ≈ **−0.5 pt 单核**（按 12 次/秒
算，是上限 —— 拖动时不采样 body），约占盒外 idle 的 1/10，但绝对值只有半个百分点。

### 整表枚举改用私有 `CGSGetOnScreenWindowList`（否决，2026-11-03）

**假设**：公有 `CGWindowListCopyWindowInfo` 为**每个**窗口构建一份描述字典 —— 服务器给它全部 key，而
仿真只读其中几个。私有路径按需取字段，并**跳过没人读的窗口**：只有 `layer == 0` 会被当地形 / 遮挡体
/ 身体（见 `architecture.md`），别的层级只花一次调用就被丢弃。

**等价性：已证实逐字段一致。** `CGSGetOnScreenWindowList(0, …)` 与公有 `[.optionOnScreenOnly,
.excludeDesktopElements]` 在在屏集合、**z 序**、level、alpha、bounds、PID 上完全相同（命令行探针逐字
段比对 + app 内 `--cgs-list-verify` **500 次比对零差异**，零回落）。两处陷阱：

- **`targetCID` 必须是 0。** 传自己的 `CGSMainConnectionID()` 返回 **0 个窗口且不报错**，看上去像
  「屏幕上没有窗口」。
- **`CGSGetWindowAlpha` 的头文件签名 `CGFloat *` 是错的，实际是 `float *`。** 按 `CGFloat` 读会把
  `float 1.0`（0x3F800000）放进 double 的低半字，得到 `5.26e-315` —— 不是 0、不是 1，而且所有窗口都
  是同一个怪值，很容易被当成「alpha 读不到」。

**owner name 私有路径拿不到**（`CGSCopyConnectionProperty` 对 7 个候选 key × 3 个 target 都返回成功
却从不写出值；`CGSGetWindowProperty` 符号已不存在；`CGSConnectionGetPID` 只给 PID，而窗口服务器自己
的连接 `cid == 0` 根本没有 PID）。名字这一列本来就因**本地化**而失效（中文系统报「程序坞」「控制中
心」），且被 `layer == 0` 完全覆盖，所以那张黑名单已**单独删除**（见 `architecture.md`）。

**性能：更贵，不是更便宜。** 两批各 6 轮交替（地板 idle，sleepiness 钉住；剔除 2 个离群 — 公有那次出
现过 2.96 / 3.40，私有组没有）：

| | 公有 `cg` | 私有 `cgs` |
| - | - | - |
| 每次枚举（`getrusage` 包住调用） | **830 µs**（803–860） | **945 µs**（872–985） |
| 总 CPU（单核） | 1.88%（1.81–1.94） | 2.08%（2.08–2.22） |
| trace 里枚举 inclusive / 15 s | 60–85 ms | 134–141 ms |

**自洽性检验**：用 `每次 µs × 12 次/秒 ÷ 总 CPU` 反推枚举占应用 CPU 的比例，两个模式都得到
**53–54%** —— 两个独立测量给出同一个占比，说明这个数是可信的。（顺带：`mean_us` 比总 CPU 稳得多 ——
同一模式下总 CPU 出过 2.96 的污染值，`mean_us` 全程在 803–985 内。）

**机制（要点）**：公有读是**一次批量调用**，按窗口摊薄约 40 µs/窗口；私有读是 **1 次列表 + 每窗口至
少 1 次、通常 4 次**服务器往返，而**单次往返**就是 ~29 µs。要在 ~19 个在屏窗口里挑出 4 个
layer-0，**至少要为每个窗口读一次 level**（trace 内 `CGSGetWindowLevel` 一项在 15 s 里占 ~100 ms，超
过整个公有枚举），这一次读 ≈ 550 µs，已接近公有一次枚举的全部成本。**「N 次小调用」赢不了「1 次批
量」：批量调用的每窗口成本与单次往返同量级。**

**所以 `CGSGetWindowBounds` 的成功不能外推。** 它赢是因为它**替代**了一个「为四个数字构建整份描述字
典」的调用；整表枚举恰恰相反，是把一次批量**换成** N 次往返。除非存在一次返回整张 level 表的私有调
用，否则这个形状没有收益空间。

**另外要更正本节上面的一个旧数字**：「一次完整枚举 ≈ 0.48 ms（~25 窗口）」来自**探针**，偏低。app 内
按 `getrusage` 直接量是 **~0.83 ms/次**，与「10 Hz 枚举是盒外 idle 最大单项」自洽（12 次/秒 × 0.83
ms ≈ 1.0 pt，约占 idle 一半）。旧数字的 0.48 ms/次 ⇒ 1.3% 本来也对不上账（0.48×12 = 0.58%）。
（2026-11-04 把桥接换成 CF 直读后，探针是 **0.86 → 0.44 ms/次** —— 同一量法，见上一节；本节那 0.83
ms 是桥接版的 **app 内**数字，「N 次小调用赢不了 1 次批量」的结论不受影响。）

## 日志的成本

一条 `writeEvent` = **45.4 µs**，其中约 **19 µs 是每行的 `stat`**（`rotateIfNeeded` 每次问文件大
小）。 `seekToEnd()` 本来就返回那个偏移、也本来就被调用，所以旋转改用它：**26.3 µs（−42%）**。没有
`fsync` 是故意的（每帧一次磁盘写会引入这次改动本来要消除的停顿）。

**教训：把诊断事件对着每帧路径审一遍。** `AirborneCaught` 曾每帧写（向上拖的窗口每帧重新接住她，累积
1252 行），即 60 × 45 µs ≈ **0.27% CPU**，与它正在记录的节省是同一量级。现在用 `ChangeGate` 折叠。

## 拖动 vs `setFrame`：为什么不能每帧移动窗口

探针（`Probes/WindowMoveProbe/`，每模式一个进程：3 s settle + 8 s IDLE + 20 s ACTIVE， `ACTIVE −
IDLE` 抵消启动尖峰/层级/合成）。`app` = 自己的 `getrusage`； `ws` = Window Server 的累计 CPU（`ps -o
time=` 每秒采样）。 **`move` 是让拖动可解释的对照：同样的鼠标运动，不移动窗口。**

| run | app Δ | ws Δ |
| - | - | - |
| 拖动面板 | **+4.05** | **+15** |
| 只移动光标 | **+3.94** | **+15** |
| `setFrame` 60 Hz（无输入） | **+6.09** | **+6.7** |

- **拖动时的窗口跟随是免费的**：`drag − move` = +0.13 pt app、+1.2 pt ws。
- **但拖动整体不免费**：仅仅移动光标就让接收事件的应用 +3.9 pt、Window Server +15 pt。这是任何前台应
  用都要付的鼠标流成本（见下一节）。
- **`setFrame` 60 Hz 是应用进程里最贵的单项（+6.1 pt）**，且完全无指针运动。这正是全屏 overlay 消除
  的成本。
- **为什么本质不同**：拖动的移动是在 Window Server 自己的鼠标跟踪循环里执行的（因为指针在动，那个循
  环本来就在跑），应用被拖，它自己不发起移动。 `setFrame` 是**每次调用**一次同步的应用→服务器 IPC +
  CoreAnimation 事务。
- **应用没有借用拖动路径的办法。** `CALayer` 位置是唯一便宜的应用驱动移动。

**这两条结论各自长成了现在默认渲染方式的一半**（见 `rendering.md`）：

- 「不移动窗口」→ 网格小窗口在**格内**只改图层位置（正是下表最后一行），窗口每 132 pt 才动一次。
- 「移动窗口很贵」→ **她快速移动时改画在一块永不移动的全屏窗口里**（`OverlayPetSurface`），那段时间
  就是下表最后一行。代价是窗口重新盖满屏；而两个触发它的状态都是短命的（见下）。

### 透明不便宜：`setFrame` 的成本与像素无关

| 模式 | app Δ | ws Δ |
| - | - | - |
| 不透明 | +5.57 | +5.62 |
| 透明内容 | +5.76 | +5.73 |
| `alphaValue = 0` | +5.40 | +4.94 |
| 静态透明窗口 + 不透明 CALayer 用 `position` 移动 | **+1.05** | **+0.34** |

- **完全透明的窗口 `setFrame` 与不透明窗口完全相同**。透明不是窗口移动成本的杠杆。
- **连 `alphaValue = 0`（完全看不见的窗口）仍要约 +5.4 pt** —— Window Server 不会跳过移动一个不可见
  窗口。所以也不是在合成内容。
- **省下的是机制，不是像素**：静态窗口 + 移动 CALayer 便宜约 5 倍。

### 有更便宜的 `setFrame`，但不够便宜，而且最后不需要（2026-11-03）

私有 `CGSMoveWindow` （探针 `_ignored/move-ab/main.swift`，每模式一个进程、60 Hz 移动，`noop` 是只跑
计时外壳不动窗口的对照，表格已减掉它）：

| 移动方式 | 实现成本（pt） | 单次调用（`getrusage` 包住） |
| - | - | - |
| `setFrameOrigin` | +6.12 | 272 µs |
| `setFrame` | +6.27 | 280 µs |
| **`CGSMoveWindow`** | **+1.41** | **32 µs** |
| `CGSMoveWindowWithGroup` | +1.72 | 70 µs |
| 静态窗口 + 移动图层（对照） | **+0.80** | 94 µs |

- **确实便宜约 4.4 倍（实现）/ 8.7 倍（单次）**，所以确实存在更便宜的 `setFrame`。
- **但 60 Hz 下 +1.41 pt 仍不便宜**：比「移动图层」那行的 +0.80 还贵，而后者是**零窗口移动**。私有调
  用只是把「移动窗口」从最贵变成第二贵，没把它变成免费 —— **不足以撑起 60 Hz 的移动**。
- **`setFrameOrigin ≈ setFrame`**，所以 AppKit 的成本不在 rect 计算里，就在那笔事务里。
- **最终没采纳私有移动，理由不是它不够快，而是不再需要了。** 它省的那 4 倍被「根本不移动窗口」整个跳
  过：网格小窗口在格内只动图层，她快速移动时干脆切到一块永不移动的全屏窗口（`OverlayPetSurface`）。
  见 `rendering.md`。

私有移动还有两条与速度无关的代价（AppKit 帧不同步、与 CA 提交不同事务），见 `platform-quirks.md`。

## 鼠标移动的开销（全屏窗口的固有代价）

移动光标把 **overlay** 应用从 ~0.75% 抬到 ~6.5%，同时 Window Server +约 15 pt。不是窗口切换（合成
CGEvent 移动流就能复现），也不是我们自己的全局事件监听。`PetController.step` 的绝对时间不变。

**实测（2026-11-03，手动四阶段 A/B，`_ignored/move-ab/measure.py`，`--mouse-move-count` 数投递 +
`ps` 计 CPU）** —— 这就是默认从 overlay 换成网格小窗口的依据（见 `rendering.md`）：

| 阶段 | overlay | 小窗口 |
| - | - | - |
| idle | 2.06% | 2.40% |
| **光标在别处持续移动** | **8.05%（+5.99）** | **1.73%（≈0）** |
| 光标在她身上移动 | 8.32%（+6.25） | 5.45%（+3.06） |
| 拖动她 | 9.32% | 9.12% |

- overlay 的 `away` 收到 **1961 次 / 15 s** mouseMoved，小窗口 **0 次** —— 差别完全在**投递次数**。
- 归一化后 **overlay 407 µs/次、小窗口 395 µs/次：单价相同**。所以「窗口小就省」的全部原因是它**只在
  指针压在她身上时才收到投递**，不是每次更便宜。
- 小窗口在 `hover` 收到 1163 次 —— 证明它**能**收事件，只是指针不在她身上时不收。这排除了「小窗口只
  是坏了所以便宜」。
- **拖动时两者持平**，因为拖动时指针本来就在她身上、小窗口也收满。所以收益在**绝大多数时间**（指针不
  在她身上时），不在拖动时。
- 方法论缺陷：那一轮**不是跨进程交替**（小窗口跑完才跑 overlay），顺序效应没排除。效应有 6 pt，不像
  顺序能解释，但严格说不满足交替要求。

**成本位置（已钉住）**：`NSEventThread` 占活跃 CPU 的 34–39%，链路是 `CGSSnarfAndDispatchDatagrams →
SLSGetNextEventRecordInternal → SLEventCreateNextEvent → PullEventsFromWindowServerOnConnection` ——
私有 SkyLight 客户端**在我们进程里**拉取并解析 Window Server 的事件数据报。主线程再加
`routeMouseMovedEvent → _routeMouseMovedEvent → -[NSWindow _reallySendEvent:]`（约 9–11%）。

**这一项是连接级的，在所有按窗口的判定之上**，这就是历史上所有窗口级/连接级开关都无效的原因（逐个实
测见 `rejected-approaches.md`）。**唯一的例外是窗口大小**：它不 gate 投递，而是让「指针下的那个窗口
是不是我们」随指针位置而变 —— 这是唯一真正有效的窗口属性。

`NSEventThread` 自身耗时（420 个 running 样本的叶子帧占比）：

| 占比 | 帧 | 含义 |
| - | - | - |
| **35.7%** | `mach_msg2_trap` | 拉取数据报的 IPC 本身 |
| 6.2% | `_kernelrpc_mach_vm_deallocate_trap` | 释放数据报的 VM 缓冲 |
| **~9%** | `SLS::TokenizedCoding::*Decoder*`、`_SLEventRecordCreateWithBytesModern` | **解码** |
| ~6% | `szone_*`、`tiny_malloc_from_free_list` | 解码路径的分配器 |
| ~4% | `CF_IS_OBJC`、`__CFDataInit`、`NSData dataWithBytes:`、`NSCFArray objectAtIndex:` | 桥接成 Foundation |
| 3.3% | `__bsdthread_ctl` | 调度 |

**所以 decode 是真实存在的（~15–20%）**，而且它发生在连接级的拉取内部，**在任何按窗口的判定之上** ——
这就是所有窗口级开关都无效的原因。各种开关的实测结果见 `rejected-approaches.md`。

## 网格渲染：两条代价轴上各退一步（默认）

到这里两条代价轴各自清楚了：

- **窗口移动**（「拖动 vs `setFrame`」「透明不便宜」）：每帧移动窗口 60 Hz 约 **+6 pt**；窗口不动、
  只移动窗口内的图层约 **+1 pt**。
- **鼠标投递**（上一节）：全屏窗口下指针在哪都收；只在她身上那块窗口里才收。

三个做法就是这两条轴上的三个点：

| | 窗口移动 | 鼠标投递 |
| - | - | - |
| 全屏 overlay（`--pet-overlay`） | **零**（窗口永不动） | **全屏**（指针在哪都在我们上面） |
| 每帧移动的小面板（旧 `--pet-panel`，已删） | **她每动一次一移**（60 Hz） | 只在指针在她身上时 |
| **网格（默认）** | **每走一个身位一次** | 只在指针压在她窗口上时 |

**机制**（`GridPetWindowController`）：窗口做成**两倍她大小**（`2w × 2w`），放在**一格她那么宽**的网
格上（`w·floor(pos/w)`），她画在窗口内的余数位置（`pos mod w`）。于是她在窗口里能走**整整一个身
位**才需要挪窗口，两次跨格之间只有她自己的 `CALayer.position` 在变 —— 而图层位置**可插值**，所以她的
移动比旧面板那个「每帧挪窗口」的阶梯**更顺**，不是更差。跨格那一帧窗口与她的图层必须同一次事务（见
`rendering.md`，用 AppKit 的移动而非私有调用就是因为这个）。

**两个状态例外，那时连这一次窗口移动也不要**：她改画在一块永不移动的全屏窗口里
（`OverlayPetSurface`）—— **被拖动**时，以及**被关在窗口里且在动**时（被抛起、或被侧壁撞击后滑动）。
两者是同一件事：她正在被快速移动。盒壁推她的速度是 **1350 / 1200 pt/s** （`maximumVelocityX/Y`），比
她自己的 92–118 pt/s 快一个数量级，所以小窗口下也是每几帧一移。并且此时用户正在直接与她交互，因此全
屏窗口不再有额外的鼠标事件开销，对截屏软件的干扰也不会被体现出来。不切换的情况：静止躺在盒底
（`isResting`），以及没有任何盒子（见 `rendering.md`）。

**代价换算**（不是实测值，是从常数折算的）：

- **窗口移动频率 = 她的速度 ÷ 格宽。** `Motion.walkSpeed = 92` / `exploreSpeed = 118`
  pt/s（`PetController` 的 `Motion` 常量；`displayScale = 1`，再乘
  `profile.movementSpeedMultiplier`），格宽 = 她的尺寸（默认 220，上面那些测量用的 132）。⇒ **约
  0.4–0.9 次/秒**，对旧面板同一场景的 **60 次/秒**（只要她在动）。
- **窗口面积 4w²**：132 时是 264×264，占开发机 1728×1177 屏的 **3.4%**，而 overlay 是 **100%**。所以
  指针压在她窗口上的时间比例远低于 overlay。

**结论：它大致上兼得两者。** 窗口移动从「每帧」降到「每格」，鼠标投递从「一整块屏」降到「她周围一小
块」—— 两条轴的代价都退到几乎可忽略的量级，代价是记账复杂（网格映射、气泡预留、拖动时换表
面）。overlay 当初赢下旧面板的那笔账（Time Profiler，30 s，同一交互脚本：拖动 **17.8% → 10.8%**，盒
内 idle **5.7% → 3.9%**；归因是旧模型每帧一次窗口移动事务，`_setFrameCommon` 2.4% +
`commit_transaction` 4.9%，新模型 0.19% + 1.3%）在这里由「每格一次」而不是「永不动」拿到，而 overlay
拿不到的那半是鼠标投递。

**htop 读数（目测，未跑 benchmark）**：在**不切到全屏表面**的场景里 —— 也就是静止和自主移动 —— 成品
的 htop 读数与 overlay 在鼠标不动时**几乎看不出区别**。这是目测，不是 A/B，它不能替代上面那节的手动
测量，只看方向。

**没测的**：网格的窗口是 264×264，比旧面板的 132×132 大，所以它的投递计数应当**介于**旧面板的 0 次与
overlay 的 1961 次之间（**推论**，按窗口面积比折算）。上面那轮 A/B 只覆盖 overlay 对旧面板，网格**没
有单独量过**。下面那节量了她的几个交互场景，但**没有一格是网格在自主走动**，所以这条缺口仍然在。

## 五场景基准：`ps` 采样 + Time Profiler（2026-11-04）

一次把五个交互场景各测两轮，回答「她动起来到底花多少」。**两个仪器从不重叠**：采样器跑在被测进程里，
带它时的 CPU 读数不是应用自己的成本（见本节末的「含采样器」列与下文）。

**口径**：每轮一次启动两段 —— 5 s settle → `ps` 15 s → 5 s settle → Time Profiler 15 s，两段之间用一
次**按键闸门**隔开（读指令、摆她的手位都不计入窗口）。头号数字是 `ps -o time=`（累计 user+sys，也就
是 `getrusage` 给的那个量）在窗口内的差 ÷ 墙钟。启动路径 `make sign` 一批一次，然后每轮 `pkill` +
`open -n` —— 与 `make rerun` 同一条 LaunchServices 路径，只是不重复重建签名（每次重建是一次
1Password 往返）。安静模式开、`sleepiness` 钉在 100。工具：`_ignored/scenario-bench/measure.py`，分
析 `top_symbols.py`。

| 场景 | 轮 | `ps` %核 | CPU s / 墙钟 s | trace 含采样器 % | trace 主线程 % |
| - | - | - | - | - | - |
| 静止 | 1 / 2 | **1.78 / 1.71** | 0.27 / 0.26 | 1.70 / 1.75 | 99.5 / 98.4 |
| 鼠标持续拖动 | 1 / 2 | **8.51 / 8.06** | 1.28 / 1.21 | 8.26 / 8.56 | 64.1 / 62.4 |
| 拖动后下坠 | 1 / 2 | **6.92 / 6.90** | 1.04 / 1.05 | 7.12 / 6.60 | 70.9 / 79.5 |
| 窗口内抛起 | 1 / 2 | **4.51 / 4.51** | 0.68 / 0.68 | 4.77 / 4.64 | 95.0 / 94.7 |
| 窗口顶部抛起 | 1 / 2 | **5.72 / 5.51** | 0.86 / 0.83 | 4.57 / 4.88 | 87.4 / 87.8 |

- **与本文档可比的两项**：静止 **1.75**（两轮 1.78/1.71）对上面私有读那节的**地板 idle 1.88 / 2.08**
  —— 低 0.13–0.33 pt，同量级，但**来源未归因**（机器状态或构建差异，没有证据）。拖动 **8.29**
  （8.51/8.06）对「鼠标移动的开销」那节的 overlay **9.32** / 旧面板 **9.12** —— 吻合，且共同印证那句
  「拖动时两者持平」。
- **本节新给的**：拖动后下坠 **6.91**、窗口顶部抛起 **5.62**。文档此前只有「拖动和下落约 30% CPU」这
  个**改进前**的起点，所以这两项是第一次有当前数字。
- 日志没有污染读数：harness 强开 `loggingEnabled`，而 trace 的 `logging` 区在各场景最大约 22 ms / 15
  s（boxthrow-r1，约 0.15 pt）。

**关键：这五个场景测的不是同一条渲染路径。** `isMovingFast = isBeingDragged ||
isMovingInsideEnclosure`（`PetController+Interaction.swift`）决定她何时改画在全屏
`OverlayPetSurface` 上：

| 场景 | 实际渲染路径 | 依据 |
| - | - | - |
| 静止 | 网格窗口（她睡着，窗口不动） | — |
| 鼠标持续拖动 | **全屏 `OverlayPetSurface`** | `isBeingDragged` |
| 窗口内抛起 | **全屏 `OverlayPetSurface`** | `isMovingInsideEnclosure` |
| 拖动后下坠 | 网格窗口 + 自由下落跨格 | 室外下落两者都不满足 |
| 窗口顶部抛起 | 网格窗口 + `liveSurface` 活读 | 站在窗沿，不在盒内 |

**所以「拖动 8.29」是对 overlay 那一列的复现，不是网格的数字。** 用这两列去解释网格的收益会错。

**`window-move` 分三档：0、2–3 ms、25–37 ms**，对「`setFrame` 是进程内最贵的非 idle 单项」（+6.09 pt
@ 60 Hz）是个直接对照：

| 场景 | `window-move` inclusive（主线程占比） |
| - | - |
| 静止 / 鼠标持续拖动 | **0 ms**（连符号都没出现） |
| 窗口内抛起 | 2 ms（0.29%）/ 3 ms（0.47%） |
| 拖动后下坠 | 25 ms（3.5%）/ 32 ms（3.7%） |
| 窗口顶部抛起 | 36 ms（5.7%）/ 37 ms（5.4%） |

拖动为 0，窗口内抛起（也走全屏表面）2–3 ms，走网格的拖动后下坠与窗口顶部抛起 25–37 ms —— 与「只有跨
格才移动窗口」一致；窗口内抛起那点残余最可能来自进出全屏表面时的窗口尺寸切换（**推论，未验
证**）。**但这里要克制** —— harness 不记窗口移动**次数**，所以「真的移动得少」与「移动了但便宜」分不
开；能确定的只是「总账很小」。网格走动（每格一次 `setFrameOrigin`）仍未测。

**两处不能直接引用本节数字的地方**：

- **`ws`（Window Server）百分比在本节不可归因。** 本节只有测量窗口内的采样，没有 IDLE 段相消，整机其
  它程序在 Window Server 里的开销全被计入（实测静止 7.7%，一被拖动就 46–50%，而她自己是 4.5–8.3%）。
  要归因必需一个「在同一台机器上拖动一个同样大小的普通窗口」的对照，**没做**。上面「拖动 vs
  `setFrame`」那节的 **ws +15 pt** 是**同进程 ACTIVE − IDLE** 得到的，两者不是同一个量，**不可比**。
- **`NSEventThread` 的占比低于本文档的 34–39%**：拖动 r1 为 **27.7%**、r2 为 **28.3%**（全线程，链路
  仍是 `__CFMachPortPerform` → `MessageHandler`），差 6–11 个点。两个候选都未测量：本条的手是**人手
  慢拖**，而 34–39% 那轮是**合成移动流**，若事件线程成本随**投递次数**走则二者本就不同量；本条的主线
  程是 907 ms / 15 s，份额分母也更大。**未解决，见 [todo.md](todo.md) §7。**

## 打开菜单时卡一下（已修）

用户报：菜单打开时整程序卡顿（下落中开菜单会看到她卡一下）。

**根因**：`StatusItemController.refreshMenuState()` 每次显示菜单都**同步** spawn
`/usr/bin/osascript` 并 `waitUntilExit()`，阻塞主线程约 100 ms（实测 96–119 ms/次）。而
`refreshMenuState` 有三个触发点，其中右键桌宠那条与前一个重复，所以约 200 ms。唯一昂贵的是「登录时启
动」的勾选状态（要走 System Events 查每个 login item）。

trace 证据（40 s，主线程 Running 1794 样本）：`StartupRegistrationService` **6.47%**，而自定义菜单视
图 **0 样本** —— 菜单自身不贵。

**方法论要点**：`waitUntilExit()` 期间主线程是 **Blocked**，而 xctrace 导出**只有 Running 行**，所
以**栈归因系统性低估阻塞型开销**，真实卡顿比 trace 里的 6.5% 更大。这与「气泡 `setFrame` 的
`commit_transaction` 没有我方调用栈」是同一类问题。

修法：缓存「登录时启动」的值（仅 nil 时读一次真值），切换后**重读真值**（注册可能失败），并去掉
`popUpMenu` 里冗余的 `refreshMenuState()`。

**代价（已接受）**：在系统设置里直接增删 login item，菜单勾选要等下次切换/重启才纠正。「既实时又零阻
塞」不可得 —— 异步读会让打开瞬间仍显示旧值。

## 拖动/下落高 CPU 的调查结论（历史）

起点是「拖动和下落时约 30% CPU」。先做路径分析，再最小风险修改，然后才转为实测剖析。两个早期优化没有
用户可见改善后，停止盲调。

- **主因是高频位置变化下的窗口系统事务成本，不是精灵绘制。** 决定性线索是用户指出「拖动时 CPU 只在鼠
  标移动时上升；鼠标不动就像 idle」。
- 有效改动：拖动期间限制昂贵刷新、下落期改为**按时间 + 距离门控**的刷新（图重建占比 21.9% → 9.7%）、
  消除无操作的窗口 frame/level 赋值、气泡不再无谓重绘。
- **最终答案不是微优化某个 API，而是换渲染架构**（全屏 overlay + CALayer），见 `rendering.md`。

## 探针必须「计数」才能信它的 CPU 读数

第一版独立探针在「光标动」与「不动」时报出相同的 CPU，而它被用来下结论。它是**无效的**：探针的窗
口**根本没有收到移动流**，所以「无变化」什么都证明不了。

替代探针镜像全屏 overlay 的窗口（borderless、non-activating、层级 2、透明），并用
`NSEvent.addLocalMonitorForEvents` **统计 `.mouseMoved`**、每阶段打印计数。它自证有效：idle **0.05%
/ 0 次**，active **2.70–2.83% / 1150–1220 次**。合成移动事件由**后台线程**发出，所以测到的是投递路
径，不掺探针自己产生事件的成本。

**规则：任何测这个开销的探针，必须展示非零的移动计数，否则它的 CPU 读数无意义。** 行为类断言同理 ——
每个私有 API 调用都要配一个**已知有效**的对照。

## 原版的 Windows 占用（作为参照）

在 Parallels 的 Win11 客户机（8 逻辑核）里跑原版 v1.3.3.0：

- idle：**~306 MiB 私有工作集**（稳定 60 s），峰值 638 MiB（启动），22–24 线程。
- CPU idle **约 11–12% 的单核 = 8 核的 1.4%** —— 任务管理器的 1–1.5% 就是这么来的。
- **`< 0.5%` 的 idle 预算只有在「多核总和」口径下才成立，而且只有我们达到**：我们的 3.4% 是 `top`
  的**单核**口径（14 逻辑核）⇒ 约 **0.24% 全核**。原版 idle 是单核 11% = **8 核的 1.4%**，它**没
  有**达到这个预算。
- 交互（拖动+放下 / 窗口抛）**无法区分**：中位数 **17.6 vs 19.9% 单核**，即比 idle 高 6–9 个点。两个
  不同物理场景成本相同，与「成本是指针而不是她的物理」一致 —— 和 macOS 探针的 `drag ≈ move` 结论同一
  形状。（尚未跑「只移动光标」的对照，所以还不能完全归因。）
- 内存只在交互期增长、**不回落**：306 → 335 MiB，交互约 +6 MiB/分钟，纯 idle 时基本平（334.2 →
  335.5）。形状像 GC 堆在分配下增长，但没有证据表明它被回收过。
