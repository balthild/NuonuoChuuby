# 未完成的工作

本文件只记**还没做的**事。已完成功能的设计理由、测量数据与踩坑记录在其余 `Docs/Internal/` 文件里（索
引见 [README.md](README.md)）；这里只留「做什么」和指向。

## 1. 角色与玩法

- **菲比啾比**。`PetCharacterProfile` 的间接层与角色专属分支（食物、捣蛋）已经就位，属增量工作，不是
  合并。
- **双宠共存 / 配对互动**。依赖菲比。
- **窗口捣蛋**（踢、藏帽、撕裂真实窗口）。整个功能尚未开工；所需辅助功能 + 屏幕录制两项权限均可接
  受，目前只是功能本身尚未开始。

## 2. 巡逻与边缘动作

背景与已修的部分见 [behavior.md](behavior.md)。

- `movementPurpose` 的 `edgeJumpApproach` / `edgeSlideApproach` **仍无生产者**：受控「从边缘跳 /
  滑」的菜单项不存在（上游对应 `StartControlledEdge`）。

## 4. 推迟的方案

- **开机自启改用 `~/Library/LaunchAgents` plist**。`StartupRegistrationService` 现在走
  `osascript`（`SMAppService` 需要 Team ID）。原先「免去 System Events 授权弹窗」的理由**已撤回** ——

  换。

## 5. 性能：还没做的

按已知收益排序。**第 2–4 项的依据是 2026-11-04 五场景 trace 的重算**（主线程 inclusive 口径）。每项
成熟度不同：有的要先补一个计数器、有的要先分类、有的要先由用户拍板 —— 都写在各条里了。

1. **Metal 渲染实验**。在干净树的独立分支做 A/B，先固定同一交互脚本与统计口径。目标是在不降低体感帧
   率的前提下，比当前 CALayer 再降低拖动 / 下落 CPU；必须优先做纹理复用（避免每帧图像上传 / 转换），
   否则可能比 CALayer 更差。trace 只量过拖动 r1：`send_message` 10.6%、`commit_if_needed` 4.4%、图像
   相关约 0.5%，指向每次提交的 IPC。Metal 能否减少提交次数未知，是否继续由用户决定。
2. **`CA::Transaction::commit()` 的调用者没有分类。** 拖动两轮里它是最大单项：295 / 223 ms，占主线程
   32.5% / 27.1%。其中多少来自我们自己的 `FrameInterpolation.animate`、多少来自框架自己发起的提交，
   还没分过；分完才知道有没有可省的提交。
3. **下落中的 `refreshForFalling`。** 六个下落轮次里它是 41–56 ms / 15 s（5.8–8.7% 主线程，约
   0.3–0.37 pt）。能不能再收紧门控没有依据：先加计数器（每秒调用次数、有几次真的重建了图），测完再
   谈。
4. **桌面图标 AX 读取：剩下的 quiet 模式那一项。** 批量取属性、记住容器元素、给遍历设界**都已做**
   （2026-11-05，见 [performance.md](performance.md) 的「批量取属性」「记住容器元素」「给遍历设界」
   三节）。仍可做的是**quiet 模式下暂停**这次读 —— 它会改变 idle 基线，所以需用户先确认要不要动。

## 6. 未测 / 未验证

- **网格渲染在自主走动时的成本未测。** [performance.md](performance.md) 的五场景基准（2026-11-04）量
  的是拖动 / 下坠 / 两种抛起 —— 前三者里有两个走全屏表面，走网格的那个是自由下落，不是走动速度档位。
  「每格一次 `setFrameOrigin`」这个网格特有成本唯一真正发生的场景就是走动，所以网格对旧面板的收益仍
  只有折算值。
- **私有 `CGSGetWindowBounds` 的收益只测过盒内 idle**。站在窗口顶边（`liveSurface`， 60 Hz）预计翻
  倍，未测；多显示器未测。等价性也只覆盖在屏窗口，见 [platform-quirks.md](platform-quirks.md)。五场
  景基准里「窗口顶部抛起」沾到了一点（`live-read` = 26 / 37 ms / 15 s ≈ 0.17 / 0.25 pt），但它没有盒
  子外的 idle 对照，不构成有效测量。
- **多显示器全未验证**（开发机单屏）。两个渲染方式都未验证，但**性质不同**：
  - overlay 每屏一块、她画在含其中心的那块上；**跨屏时会被 overlay 的窗口边界裁切**。
  - 默认的网格小窗口只有一个、跟着她走，所以没有裁切问题；但它的**网格映射、气泡预留、形状点**都没在
    多屏下量过，拖动表面（盖所有显示器并集）也没试过跨屏拖。
  - AX 桌面图标在负坐标（第二显示器在左侧）下的表现也未验证。
- **多屏混合 DPI 未验证**。全程用点规避了大部分换算，但没有真实混合 DPI 组合的实测。
- **原版 Windows 的交互成本未归因**：拖动后下落与窗口抛起两个场景成本相同，提示成本可能来自指针输
  入，但没有跑「只移动光标」对照。

## 7. 待查的线索

- **`NSEventThread` 占活跃 CPU 的份额对不上。** [performance.md](performance.md) 的「鼠标移动的开
  销」记 34–39%，而五场景基准的拖动轮是 **27.7%（r1）/ 28.3%（r2）**，差 6–11 个点。两个候选都未测
  量：（a）事件线程成本可能随**投递次数**走，而基准是人手慢拖、34–39% 那轮是合成移动流；（b）基准的
  主线程同时在合成与 tick（907 ms / 15 s），份额分母更大。要判定需要同时记 `mouseDragged` 的投递次
  数、并把主线程工作量控成常数。
- **「落地成功，下一帧 perch 被判 covered」**。落地用 `isVisible(atCoordinate:inset: 10)`（更
  严），perch 用 `isVisible(at:)`（inset 0，更松）；同一张图上不可能严过而松不过，所以两者之间图被重
  建过。不是那次改动引入的。已加 `PerchCovered` 诊断，至今未触发。详见 [physics.md](physics.md) 文
  末。
